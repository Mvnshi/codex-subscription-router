# Keeping up with the official app

OpenAI ships a new build of the ChatGPT/Codex desktop app about every day: on macOS through an update
feed, on Windows through the Microsoft Store (package `OpenAI.Codex`; the two platforms share app builds,
so Store package `26.930.3930.0` is the same app as macOS build `12947`). The router is a patched copy of
that app, so each new build has to be checked. Most of that is automatic.

## The loop

```text
 every 6 hours   upstream-watch.yml   reads the macOS feed and the Store catalog, compares the newest
                                      builds with scripts/recorded_builds.json and the TESTED tables,
                                      and opens or updates ONE tracking issue per platform
 every day       upstream-canary.yml  installs the newest build on a clean runner, runs the real
                                      installer against it, and (Windows) boots the patched app;
                                      writes the result into the tracking issue
 a person (or    scripts/record_build.py   adds a passing build to the recorded builds, and a pull
 an assistant)                             request lands it
```

A build nobody has recorded is never refused. The installers explain that it is newer than the recorded
builds and ask (`--check-source` exits 3 for exactly this), and every patch step checks the app and stops
by itself if it changed. Recording a build only removes the question.

## The three levels

| Level | Meaning | Where it lives |
| --- | --- | --- |
| **Tested** | Checked by hand against [SMOKE-TEST.md](SMOKE-TEST.md) as far as [COMPATIBILITY.md](COMPATIBILITY.md) says | `TESTED_SOURCE_BUILDS` (macOS) and `TESTED_WINDOWS_SOURCE_BUILDS` (Windows) in the patchers |
| **Verified by the canary** | Patched with every anchor matching on a clean runner, and on Windows booted (control API healthy, window drew its page). Routing, switching and failover were not re-run on it | `scripts/recorded_builds.json`, shown in the table in COMPATIBILITY.md |
| **Not recorded** | Anything else | Asks first |

Only a person promotes a build to **tested**, by editing the table in the patcher and adding evidence to
COMPATIBILITY.md. The canary's "verified" is deliberately a weaker statement.

macOS builds are not recorded as verified until the canary can also start the app on a macOS runner;
today it reports whether it started, and the patch and signature check decide the result.

## When the canary passes: record the build

1. Download the run's `canary-<platform>` artifact (the tracking issue links the run), or take the JSON
   the issue shows.
2. `python scripts/record_build.py canary-windows-x64.json` (add `--dry-run` to preview). It refuses a
   result that did not pass, lacks the facts it needs, or disagrees with what is already recorded.
3. Run the checks (`python -m unittest discover -s scripts -p "test_*.py"`, `python scripts/check_release.py`),
   add a CHANGELOG line, and open a pull request. The table in COMPATIBILITY.md is regenerated by the
   script and a test fails if it drifts from `recorded_builds.json`.
4. When the pull request merges, the next watcher run closes the tracking issue.

An assistant can do all of this: ask it to handle the tracking issue following this file.

## When the canary fails

The result's message is the first error the installer printed. Typical causes, in the order they occur:

- **`expected N ... found M`** in an anchor: the official app changed in a way the patch does not cover.
  Find what changed, update the pattern **deliberately and exactly** (never loosen a count to make a build
  pass), and add a test. A count that is simply different in the new build, such as "Computer Use
  references in app.asar", is a one-line table change once you have looked at why.
- **`could not find ...`**: a minified name moved. Capture the new name from the bundle and keep the anchor
  exact.
- **Patched but did not boot** (Windows): the page loaded nothing or the control API never answered. The
  artifact has the installer log; run `scripts/boot-check.ps1` locally.

To investigate a **macOS** failure without a Mac, run the asar-editing steps against the real build on any
computer:

```sh
npm ci --ignore-scripts
python scripts/probe_mac_asar.py --latest        # or --zip a-build-you-have.zip
```

It extracts the build's `app.asar` and reports the first of the three steps that fails. The native steps
(signing, helper layout) still run only on macOS; push to a branch named `canary/anything` to run them on a
real macOS runner with the whole workflow. On Windows the patcher runs directly against the installed Store
app (`python scripts\patch_app_windows.py --check-source`, then without the flag and with
`--allow-untested-source` to try it).

## Rules that do not bend

- Anchors are exact and fail closed. A review that makes a build pass by relaxing a check is not a fix.
- Say what was verified and what was not, in COMPATIBILITY.md; the README and website repeat only that.
- Never commit an app bundle, an `.exe`, signing material, account data or a token. Releases are source-only.
- The canary only reads and builds. It never publishes anything; its only write permission is to issues.

## Releases

Follow [RELEASING.md](RELEASING.md). A release states plainly which Windows and macOS builds it was
checked on and that the Windows port is provisional until SMOKE-TEST.md is complete for it.
