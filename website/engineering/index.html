Subscription Router/Engineering

How the ChatGPT
subscription router works.

A local desktop tool for a practical problem: using multiple subscriptions without losing track of accounts, usage, or the conversation you’re already in.

One connection. Isolated accounts.

The ChatGPT subscription router builds an independent copy of the desktop app. A small Go multiplexer sits between the desktop interface and the official account engines. The interface opens one app-server connection; the router manages one child process per connected subscription.

Each child keeps an isolated Codex home. Authentication and account state stay separate, while the router maintains a persistent mapping from chat IDs to their owning accounts. The official desktop installation remains the build input and is not modified.

New-chat routing considers quota that may expire before its next weekly reset, short-window pressure, and a bounded boost for banked reset credits. It does not just send every request to the account with the highest percentage left. The landing-page demo uses simplified, illustrative account data.

Read the request flow and routing architecture.

Keep the thread where it belongs.

Follow-up requests normally return to the original account. Moving a conversation on every turn would discard useful account-level continuity and create unnecessary cross-account state changes.

When an account is depleted, the router can move the chat to an account with capacity. The newer engine rejects a foreign session path, so successful failover needs more than changing an account ID: the chat rollout must be copied into the target account’s session directory and resumed from a path that engine accepts.

A cached target writer also needs to be shut down before the session is refreshed. The maintained implementation uses archive and unarchive to await that shutdown, validates session paths and symlink parents, and prevents a move while descendant tasks are active. The checks are designed to preserve both earlier context and later follow-up messages when a chat moves back and forth.

Read the failover investigation.

Desktop compatibility is part of the product.

The router patches a known desktop bundle, so an upstream update can change renderer structure, native helpers, or integrity checks. The patcher checks version, build identity, and patch anchors and stops when they do not match. That makes compatibility a recorded result rather than an assumption.

Build 12246 introduced an Electron integrity change that rejected rebuilt archives at launch. The maintenance work traced the additional authentication of the integrity dictionary to an embedded framework digest. Updating that digest alongside the archive metadata allows the independent app to launch while keeping integrity verification enabled.

Native Computer Use also needs a separately identified and signed helper so macOS can grant the router its own permissions. Live testing exercised native clicks and keyboard input through that managed helper.

Read the build 12246 port notes and test limits.

Windows: start from how the app really ships.

The first Windows port assumed the desktop app came from a per-user installer, and it refused Microsoft Store packages on the belief that a copy would neither read completely nor launch. OpenAI ships the Windows app only through the Store, so that port could never run for anyone. Reading the actual package showed the belief was wrong: the owning user can read every file, the package’s app directory copies to an ordinary folder, and the copy launches.

The patcher now finds the package through the Windows package registry, takes the host executable from the package manifest instead of guessing among seven top-level executables, and copies the app read-only. The original app only relocates its engine when it runs from the Store’s protected directory, so the copy runs the router’s multiplexer directly with the original engine beside it. The official package’s hash and signature are unchanged after a build.

Three things only the real build could reveal:

  • Repacking the app archive by top-level package also unpacked deeply nested JavaScript and produced a directory path over Windows’ limit. The patcher now reads the official archive’s own packed and unpacked flags and requires the repacked archive to keep exactly the same set: 48 entries out of 21,032 paths.
  • Windows binds a tray icon’s fixed identity to the first executable that registers it, so the copy had no tray icon and nothing to quit it from. Each known identity is now replaced with the router’s own, and the shell’s registry confirms the copy registered it.
  • The app’s own protocol registration never runs on Windows, and a renamed minifier variable broke one renderer anchor. Both are handled with exact anchors and tests for the near-misses; every other registration still stops the patch.

The rule stayed the same as on macOS: anchors are not loosened to make a build pass. A fix is a precise new anchor with tests, or the build is refused.

A gateway in the middle changes what the router can see.

The router’s account engines inherit the Codex configuration. If that configuration sends model traffic through a local gateway that answers a quota error by switching to another provider, the router never sees a usage-limit error, so it cannot fail a chat over mid-turn. It still moves a chat before sending when an account’s usage shows it is spent, because that check reads the account’s usage rather than the model traffic. What it cannot do is let the gateway serve a new chat when every subscription is spent: it refuses the chat and says so.

Two related facts matter when both apps are installed. The official app and the router share one chat store, so each lists the same chats, but a chat runs on the engine of whichever app it was sent from. Only the router’s window routes between subscriptions.

For people who want the router to own the fallback, an opt-in setting (an environment variable, or a one-line file in the router’s state folder) starts only the router’s engines on a named provider such as the built-in one. It is off by default, leaves the Codex configuration and other Codex apps alone, and an invalid value stops the router with a message naming where it came from instead of being ignored. On the Windows build, a chat started without naming a provider reported the built-in provider and a real turn completed. One model-list request at engine start still uses the configured provider.

The setting and its details are in the README.

Spending a reset is a deliberate action.

Reset credits belong to their subscriptions. The UI fetches each account’s balance independently, distinguishes pending data from failed requests, and shares in-flight requests between the account picker and the native usage sheet.

The default policy is Ask me. Manual redemption goes through a policy-aware helper and requires confirmation. Automatic use is an explicit opt-in: ordinary account failover comes first, and a reset is considered only when the usable pool is depleted.

Automatic attempts are serialized across the pool and use a cooldown. A request whose response is lost can still have spent a credit on the server, so an uncertain outcome stops further pool redemption instead of continuing to the next account. Fake-credit tests cover declined confirmation, eligibility, policy changes, and uncertain responses.

Inspect the reset policy implementation.

Keeping up with an app that changes daily.

OpenAI ships a new build of the desktop app about every day, on macOS through an update feed and on Windows through the Microsoft Store. The two share app builds, so Store package 26.930.3930.0 and macOS build 12947 are the same app. A patch that matches exact anchors in that app has to be re-checked against each one, so the project does that on a schedule instead of by hand.

  • Watching. Every few hours a workflow reads the two public feeds, without downloading the app, compares the newest builds with the ones the project has recorded, and keeps one open issue per platform while the newest is unrecorded. One rolling issue, not one per build, so the tracker stays readable.
  • Testing the real thing. Every day a canary installs the newest official build on a clean macOS runner, a Windows runner and a real Windows 11 ARM64 runner, runs the project’s own installer against it, and on Windows starts the patched app and checks that the multiplexer’s control API is healthy and the window drew its page (a blank window doesn’t count). The result is written into the platform’s issue.
  • Recording. A build that passes is recorded as verified by the canary, a weaker level than a build tested by hand (routing and failover were not re-run on it). The installers accept it without asking. A build nobody has recorded is never refused: the installer says so in plain words and asks, and every patch step still stops by itself if the app changed.

It already earned its keep. On the first runs the newest Windows build installed, patched and started on x64 and on real ARM64 Windows, which closed a gap that had been listed as untested. The newest macOS build failed on a count of Computer Use references that had drifted from 17 to 16, which was a one-number fix; the build after that changed the profile menu, which is not fixed yet, and the canary says so every day until it is.

The whole routine is written down, in a form an AI assistant can follow as well as a person.
